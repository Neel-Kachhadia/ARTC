Fully source-built old-stack TSan control
=========================================

The minimal callback RPC reproducer was built without ARTC against the exact
gRPC v1.51.1 release checkout and its direct dependency gitlinks. All gRPC,
Abseil, Protobuf, BoringSSL, c-ares, RE2, and zlib C/C++ dependency objects in
the resulting binary were TSan-instrumented and statically linked. The TSan,
libstdc++, and libc runtimes remain dynamic.

The first attempt to compile every gRPC v1.51.1 dependency as C++23 failed in
Abseil 20220623 at `absl/time/clock.cc:199` (`constinit` with a non-literal
SpinLock) under GCC 13.3. The controlled old-stack build uses gRPC's C++17
source mode, while the reproducer target itself remains C++23. This matches
the older library's supported source mode and keeps the application standard
under test.

Results from 130 fresh processes:
  clean startup/call/shutdown: 124
  TSan reports:                6
  other failures:              0

All six reports have the same Abseil startup signature: main-thread
`Waiter::Post()` atomic write in `absl::synchronization_internal` overlaps a
TSan-observed `mmap` write from `LowLevelAlloc` while a gRPC default-executor
thread initializes its `ThreadIdentity` and enters `CondVar::WaitCommon`.
The program contains no ARTC code. The complete representative report is in
`old-source-startup-race.txt`; individual reports are retained in
`/tmp/artc-tsan-oldsource-1511-cxx17deps-runs/`.

This establishes that the old source stack itself can produce a TSan startup
report when fully instrumented. It does not prove the report is a source-level
memory-safety defect: the observed write comes from TSan's mmap interceptor,
and its signature differs from the packaged GraphCycles/epoll reports.
